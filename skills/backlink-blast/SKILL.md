# 铺设海量外链

**触发方式**：用户消息以 `/backlink-blast` 开头时激活。

读取 `urls/{域名}.json` 中的 URL 列表，针对每个 URL 检查已铺设平台，找出缺铺的 (URL, 平台) 组合并执行铺设。

## 执行流程（Claude 全自动）

### Step 1：读取 URL 与平台覆盖状态

1. 读取 `urls/{域名}.json`，获取该域名下所有 URL 及各 URL 的 `platforms` 记录。
2. 根据策略确定**本轮目标平台列表**（来自 `platform-success-rate.md` 的高成功率平台 + 配额内的新探索平台）。
3. 遍历每个 URL，检查其在目标平台上的覆盖状态，生成**缺铺清单**（URL + 未覆盖平台的组合）。
4. 若缺铺清单为空，记录"所有 URL 已覆盖本轮目标平台，执行结束"，直接归档并退出。
5. 自主生成锚文本策略（品牌词、长尾词、纯 URL 等，视页面内容而定）。

### Step 2：外链铺设

对筛选出的 URL 列表，逐个执行外链铺设。

#### 策略思考框架

**不要机械执行固定平台列表。** 针对每个 URL 独立分析，自主决策最优渠道。

##### 第一步：分析目标

先理解 URL 的本质，再决定去哪里铺：

- **内容类型**：博客文章？产品页？工具/开源项目？本地服务？
- **行业领域**：技术/开发者？电商/消费？教育？本地生活？娱乐？
- **语言/地域**：中文？英文？多语言？主要受众在哪里？
- **锚文本方向**：品牌词？长尾关键词？纯 URL？需自然融入语境？

**关键词与平台一致性要求**：

- 外链铺设的关键词必须与目标域名的主要内容保持一致。例如：目标域名为中文网站，则锚文本应使用中文关键词；目标域名为英文网站，则使用英文关键词。
- 铺设平台的选择应尽量与目标域名语言和受众一致。中文网站优先选择中文平台，英文网站优先选择英文平台。

##### 第二步：评估渠道维度

从以下维度自主筛选最优渠道，而非背诵固定清单：

| 维度 | 评估要点 |
| --- | --- |
| **权重传递** | dofollow vs nofollow？页面权威度？是否带 `rel="ugc"` / `rel="sponsored"`？ |
| **审核门槛** | 注册难度？内容审核严格度？是否需要实名/手机号？ |
| **存活周期** | 链接多久会被清理？平台对推广内容的容忍度？ |
| **相关性** | 平台受众与目标内容的匹配度？ |
| **成本** | 是否完全免费？是否需要时间/人力成本？ |
| **可规模化** | 能否快速批量复制？ |

##### 第三步：选择策略方向

根据目标分析结果，自主组合以下方向（不限于此，可创造新策略）：

- **平台发现**：主动搜索和测试从未使用过的外链平台。通过搜索引擎、竞品分析、行业论坛等渠道挖掘新机会，扩大可用平台池。
- **内容寄生**：在允许用户生成内容的平台发布高质量文章/帖子，自然植入链接。优先选择权重高、审核松、内容长期存活的位置。
- **社区渗透**：在论坛、问答、讨论区中以有价值回答/评论的形式植入链接。关键是先提供价值，再附带链接。
- **资源投放**：将目标内容包装为可下载资源（PDF、文档、代码仓库、工具），投放到资源聚合平台。
- **媒体曝光**：通过新闻稿、客座博客、PR 等方式获取编辑型外链。
- **资产构建**：利用免费基础设施（GitHub Pages、Vercel 等）搭建卫星站/着陆页，形成可控外链网络。
- **社交裂变**：利用社交平台的传播机制，通过话题、标签、互动扩大内容曝光，获取自然转发带来的间接外链。

##### 第四步：平台频率控制

**避免对同一平台同时提交大量外链**，防止触发封禁机制：

- **单平台上限**：同一轮执行中，对单个平台的提交数量不超过 5 个外链。
- **间隔策略**：同一平台的多条外链提交之间，至少间隔 3 个其他平台的提交。
- **轮换机制**：优先将 URL 分散到不同平台铺设，而非集中轰炸单一平台。
- **历史记录校验**：读取 `platform-submission-log/{YYYY-MM-DD}.json`，检查当天已向某平台提交的总量，若超过 10 个则暂停该平台，选择其他渠道。

##### 第五步：动态调整

执行过程中持续评估效果，实时调整：

- 某个平台连续失败？跳过，记录原因，换下一个。
- 发现某个渠道效果特别好？加大投入，复制模式（但仍需遵守频率控制）。
- 遇到验证码/封禁/人机验证？尝试绕过或记录后切换渠道，不要卡住不动。
- 目标 URL 的内容属性特殊？创造性地寻找匹配它的 niche 平台。

##### 第六步：平台探索纪律

**禁止只使用已知成功平台。** 每次任务必须主动探索新渠道，避免陷入平台舒适区：

- **新平台配额**：每轮铺设中，至少对 1 个从未使用过的平台发起尝试（任务量 >= 10 个 URL 时，至少尝试 2 个新平台）。
- **探索触发条件**：
  - 任务开始时，先检查已使用平台列表，若发现连续 3 次以上任务都依赖同一批平台，必须强制探索新平台。
  - 当常用平台出现封禁、审核变严、成功率下降时，立即启动新平台搜索。
- **探索方法**：
  - 搜索当前年份的外链平台推荐。
  - 根据目标内容类型搜索垂直平台。
  - 分析竞品外链来源，寻找被忽视的平台。
- **探索记录**：所有新平台尝试必须记录到本次详情文件中，包括平台名称、尝试结果、失败原因（如有）。
- **探索保护**：新平台的尝试不计入成功率考核，避免因初期失败而被快速弃用。同一新平台至少尝试 3 次后再评估是否停用。

### Step 3：更新状态

每个 (URL, 平台) 组合铺设成功后，将该平台名追加到 `urls/{域名}.json` 中该 URL 的 `platforms` 数组：

```json
"platforms": ["telegra.ph", "rentry.co", "web.archive.org"]
```

- **铺设成功** -> 将平台名追加到 `platforms` 数组
- **铺设失败** -> 不记录，由全局成功率文件管控是否继续使用该平台
- **主动跳过** -> 不记录，换其他平台继续尝试

外链 URL、日期、失败原因等详情记录在 `.agent-memory/blast/history/{日期}-{时分}.md` 中，不在此文件重复存储。

### Step 4：记忆归档

将铺设结果归档到 `.agent-memory/blast/` 目录。

## 全自动执行宣言

Claude 在本项目中具备以下能力，**不需要人类手动操作**：

1. **浏览器自动化** — 通过 chrome-devtools MCP 打开网页、填写表单、点击按钮、完成人机验证（如需）。
2. **内容生成** — 自动生成符合平台调性的文案、标题、描述，避免被识别为垃圾信息。
3. **账号管理** — 自动记录注册信息、Cookie、Token，维护多平台账号状态。
4. **链接追踪** — 自动记录已发布的外链 URL，生成外链分布报表。
5. **错误恢复** — 遇到验证码、IP 限制、封禁时，自动切换策略或跳过并记录。
6. **结果汇报** — 执行完成后自动生成外链铺设报告，包含 URL 列表、平台分布、预计权重传递效果。

## 状态持久化文件

- `urls/{域名}.json` — **按域名隔离**，存储该域名下所有 URL，`platforms` 字段为字符串数组，仅记录已成功铺设的平台名
- `accounts.json` — 注册账号信息（统一存储，明文，方便复查与复用），存放于项目根目录（持久化文件）
- `platform-submission-log/{YYYY-MM-DD}.json` — 各平台按日期拆分的提交记录（仅记录各平台当日提交次数，用于频率控制），存放于 `platform-submission-log/` 目录（持久化文件，不放入 tmp）
- `scripts/` — 自动化脚本统一存放目录（如浏览器自动化脚本、批量提交脚本等）
- `tmp/` — **临时文件目录**。执行过程中产生的临时文件（缓存、截图、调试日志、中间 HTML、Cookie 文件等）一律存入此处。该目录已被 `.gitignore` 排除，不会被 git 追踪。

## 记忆系统

### 节点格式（插入 `.agent-memory/blast/index.md` 顶部）

```markdown
- **{YYYY-MM-DD HH:mm}** | [blast] | {目标域名} | 铺设{n}个外链，成功{m} | [{status}] | [详情](history/{文件名}.md)
  - 备注：{平台表现、异常、优化建议}
```

### 详细记录文件（`.agent-memory/blast/history/{日期}-{时分}.md`）

**包含内容**：

- 铺设概览（日期、目标域名、待铺设URL数）
- 每个平台的执行详情（账号、内容摘要、外链URL、状态、异常备注）
- 成果统计（尝试/成功/失败平台数、外链总数）
- 外链清单（平台 | URL | 锚文本 | 状态）
- 备注（异常分析 + 优化建议）

### 平台成功率记录

维护 `.agent-memory/blast/platform-success-rate.md`，记录各平台的历史表现，方便后续任务优先选择高效平台：

```markdown
| 平台 | 总尝试 | 成功 | 失败 | 成功率 | 最后尝试日期 | 备注 |
|------|--------|------|------|--------|--------------|------|
| 知乎 | 12 | 10 | 2 | 83% | 2026-05-14 | 审核较严，需高质量内容 |
| CSDN | 8 | 7 | 1 | 88% | 2026-05-14 | 技术类内容效果极佳 |
```

**记录规则**：

- 每次任务结束时更新此表。
- 成功率 = 成功数 / 总尝试数，保留整数百分比。
- 备注栏记录平台特性变化（如审核变严、封号风险、文案偏好等）。
- **优先使用成功率 >= 70% 的平台**，成功率 < 30% 的平台暂时停用，一个月后再试。
- **新平台单列**：在表尾单独列出"新平台尝试"区域，记录本次首次尝试的平台（无论成败），方便后续评估是否纳入常规平台池。

### 记忆流程

1. **任务启动时：读取历史记忆**
   - 读取 `.agent-memory/blast/index.md`，了解各平台过往的表现。
   - 读取 `.agent-memory/blast/platform-success-rate.md`，优先选择成功率高的平台。
   - **吸收历史经验直接指导本次策略**：上次铺设时哪些平台效果好、存活率高？哪些平台已封号或审核变严需要避开？哪些文案策略被验证有效？哪些渠道是时间陷阱（投入大产出低）？
   - 按当前日期+时分生成文件名（如 `.agent-memory/blast/history/2026-05-14-1430.md`）。
2. **执行过程中**：实时写入铺设事件到详情文件。
3. **任务结束时**：
   - 完善详情文件中的统计和备注
   - 更新 `.agent-memory/blast/platform-success-rate.md` 中的平台成功率数据
   - 在 `.agent-memory/blast/index.md` 顶部插入 `[blast]` 类型节点
   - history 文件已包含完整执行记录与结果汇总，无需额外报告文件

## 输出物

每次执行结束后，Claude 自动生成并保存到项目目录：

- `.agent-memory/blast/index.md` — 更新后的任务索引（blast 铺设节点）
- `.agent-memory/blast/history/{日期}-{时分}.md` — 本次任务的完整执行记录（含策略、明细、统计、优化建议）
- `.agent-memory/blast/urls/{日期}-{时分}.txt` — 所有外链 URL 列表（方便批量提取）
- `.agent-memory/blast/platform-success-rate.md` — 各平台成功率统计表（持续更新）
- `platform-submission-log/{YYYY-MM-DD}.json` — 各平台按日期拆分的提交日志（用于频率控制，持久化文件）

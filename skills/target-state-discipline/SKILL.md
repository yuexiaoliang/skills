# Target State Discipline

目标：**交付像“今天根据当前需求一次性设计出来”的最终状态，而不是一层层补丁累积出来的状态。**

用户当前指令优先。这个 Skill 不能用来删除用户明确要求保留的历史、迁移兼容、审计记录、公开 API 契约或数据迁移能力。

## 1. 先冻结当前目标，不先改文件

在动手前，用内部工作记录写一份极短的 `TARGET STATE`：

- 当前用户真正要达到什么结果？
- 哪些约束现在仍然有效？
- 哪些旧目标已经被明确放弃？
- 哪些兼容义务是真实存在的？由谁或什么外部对象要求？
- 哪些内容只是修改过程的历史，而不是最终产品需求？

不要把“之前讨论过”“之前实现过”“可能以后会用”自动算作保留理由。

**规则：没有当前目标或真实兼容义务支持的内容，默认候选删除，而不是默认保留。**

## 2. 对现有内容做四类判定

逐项判断代码、文档、配置、测试、目录、注释、API、提示词和数据结构：

- **KEEP**：直接服务当前目标，保持即可。
- **CHANGE**：目标仍需要，但现有表达或实现不合适。
- **DELETE**：只为旧目标、旧补丁、旧流程、已废弃行为或不再存在的风险服务。
- **COMPAT**：确有外部兼容义务，暂时不能删除；必须能说清兼容对象、失败后果和退出条件。

不要创造第五类“先留着以后也许有用”。

如果无法说明某段内容属于 KEEP / CHANGE / COMPAT 的依据，它应进入 DELETE 候选。

## 3. 使用“今天从零做还会加吗？”反事实检查

对每个可疑项问：

> 如果今天第一次看到当前需求，没有经历之前的讨论和实现历史，我还会主动加入这一行、这个分支、这个文件、这个配置、这个说明吗？

如果答案是否定的，且没有真实兼容义务，删除它。

典型残留包括：

- “以前……现在……”式的产品/课程正文；
- 为已经放弃的方案写的例外、否定句和防护规则；
- 已不使用的 feature flag、环境变量、配置项；
- 旧 API alias、wrapper、adapter、fallback；
- 已失效 TODO、迁移注释和临时兼容分支；
- 为修复前一个补丁而新增、但新设计已不需要的补丁；
- 文档里解释一次性事故、PR、上传失败或历史决策过程；
- 测试仍在锁定已经放弃的行为；
- 新旧名称、目录、概念或状态并存；
- “禁止 X”只因为旧版本曾经错误地做过 X，而当前设计根本不会产生 X。

## 4. 不要用“追加限制”代替真正重构

发现旧内容与新目标冲突时，优先问：

**能否直接删除或重写旧结构？**

不要默认采用：

- 再加一个 if；
- 再写一段“注意：旧规则不再适用”；
- 再增加一个 wrapper；
- 再加一层兼容别名；
- 再写一份新文档解释旧文档；
- 再增加一个 Skill 去抵消另一个 Skill；
- 再加一条测试去允许两个互相矛盾的行为同时存在。

当用户允许破坏性重构，或者没有真实兼容义务时，**替换旧结构通常优于叠加补丁。**

## 5. 代码任务的专门规则

### 5.1 单一行为路径

同一能力尽量只有一个当前实现路径。旧实现已被替代时，删除旧入口、旧 helper、旧类型和旧测试，不通过隐藏分支继续保留。

### 5.2 兼容必须有证据

保留兼容代码前必须能回答：

- 兼容谁？
- 当前仍有调用者/数据吗？
- 删除会具体破坏什么？
- 什么时候可以删除？

“也许有人在用”不是证据。

### 5.3 修改行为时同步删除旧约束

改动一个接口或状态机后，搜索并处理：类型、调用点、测试、fixtures、配置、日志、注释、文档、示例、命令、错误信息、监控和迁移代码。

不要只让主路径变正确，而让外围继续讲旧故事。

### 5.4 测试目标状态，而不是补丁历史

测试应验证最终行为和关键不变量。删除只为旧实现细节存在的测试。

如果某个被废弃概念特别容易复活，可以加入“负向约束测试”，例如：

- 仓库中不得再出现某旧配置名；
- 公共 API 不得再暴露旧字段；
- 只有指定迁移目录允许出现旧 schema 名称。

负向测试应保护目标状态，不应永久记录一次偶然事故。

## 6. 文档与提示词任务的专门规则

规范性文档只描述**现在是什么、现在为什么、现在怎么做**。

除非历史本身对操作有价值，否则这些内容移出主文档：

- 之前为什么做错；
- 哪次 PR 修了什么；
- 曾经考虑过哪些已经放弃的方向；
- 为何某个旧文件已删除；
- 一次工具失败、上传失败或沟通误解的经过。

需要历史时，放在 Git 历史、CHANGELOG、ADR、迁移指南或专门 archive 中，而不是污染当前入口。

**不要通过写“X 不再是目标”来保留 X。若 X 已与当前任务无关，直接不提 X。**

## 7. 做“残留扫描”而不是只看改动文件

完成主要修改后，对整个相关作用域搜索：

- 已废弃名词、旧名称、旧路径；
- 旧环境变量、命令、配置字段；
- `legacy` / `deprecated` / `temporary` / `compat` / `fallback` / `old` 等标记；
- “以前 / 之前 / 不再 / 已废弃 / 为了兼容 / 临时 / 后续删除”等历史语言；
- 重复的规则、重复 source of truth；
- 旧测试、旧 fixture、旧截图、旧示例；
- 被删除功能的文档链接和 imports。

搜索结果逐项分类，不机械删除。真实迁移材料和历史目录可进入允许列表。

## 8. 做一次“冷启动审查”

最终提交前，假装你从未看过修改过程，只看当前需求和最终仓库/文档，然后问：

1. 我能否仅凭最终状态理解系统？
2. 是否存在只有知道历史才能理解的句子、分支或文件？
3. 是否有两个地方同时定义同一个当前事实？
4. 是否有旧概念虽然被否定，却仍占据认知空间？
5. 是否有代码只为过去的错误补丁服务？
6. 如果删掉所有 Git 历史，当前版本是否仍自洽？

任一答案暴露历史依赖，就继续清理。

## 9. 完成门槛

任务只有在以下条件满足时才算完成：

- 当前目标可以独立描述，不依赖旧方案；
- 最终实现与当前目标一致；
- 已废弃内容在正常入口中消失；
- 真实兼容义务被明确隔离，而不是散落全局；
- 代码、测试、文档、配置和示例讲同一个故事；
- 全作用域残留扫描完成；
- 冷启动审查通过；
- 验证结果只声称实际检查过的范围。

## 10. 输出方式

完成任务时，优先报告最终状态和验证结果。除非用户要求，不要把大量清理历史写进最终产品或最终回复。

如果确实保留了 COMPAT 内容，简短说明保留原因和退出条件；不要用“谨慎起见”作为理由。

如果用户要求完全重写或明确“不在意已有内容”，将这视为强信号：**不得为了保留工作量、历史连续性或自己之前做过的东西而降低重构力度。**

维护/评审本 Skill 时，可按需读取 `references/review-cases.md`。

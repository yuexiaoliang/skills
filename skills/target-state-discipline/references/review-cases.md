# Target State Discipline 回归案例

这些是行为规格，不代表已经对所有模型执行过测试。

| 场景 | 应做 | 不应做 |
|---|---|---|
| 用户先要 A，后来明确改成 B | 重新以 B 建 TARGET STATE，删除只服务 A 的内容 | 保留 A 并补一句“A 只是未来选项” |
| 旧代码有兼容 wrapper，但没有调用者 | 删除 wrapper、类型、测试和文档 | “保险起见”继续保留 |
| 公共 API 仍有真实外部调用者 | 标为 COMPAT，隔离兼容层并记录退出条件 | 为追求干净立即破坏外部契约 |
| 用户允许完全重构 | 重新设计最终结构，迁移有用事实即可 | 把旧目录逐层套进新目录 |
| README 解释一次历史上传失败 | 删除正文历史；需要时留 Git/PR 记录 | 写更多说明解释为什么它不重要 |
| 新实现让旧 feature flag 无意义 | 删除 flag、分支、配置、测试和示例 | 永久保留 `if legacy_mode` |
| 修 bug 曾叠加三层特殊分支 | 根据当前不变量重写成单一路径 | 在第四层继续加补丁 |
| 旧术语只在迁移说明中合法存在 | 允许迁移目录出现，主代码和主文档禁止 | 全仓机械删除导致迁移文档失真 |
| 测试锁定旧实现细节 | 重写为目标行为测试 | 让新代码同时满足新旧内部结构 |
| 文档写“不要再生成四课成品” | 改成通用规则“只准备当前小步” | 永久记录那次事故 |
| Skill A 与 Skill B 冲突 | 收敛 source of truth，删除重复规则 | 再新增 Skill C 解释优先级 |
| 用户问“为何还保留旧概念” | 检查是否有真实当前理由；没有则承认残留并清理 | 为过去的决定事后制造理由 |

## 重点测试问题

评审一个模型执行结果时，检查：

1. 它是否先重新表达当前最终目标，而不是从上一个补丁继续？
2. 它是否能删除自己此前创建的内容？
3. 它是否把“历史存在”误认为“当前需要”？
4. 它是否因为担心未来可能性而保留无证据兼容？
5. 它是否能发现文档、代码、测试和配置里的同源残留？
6. 它是否进行了仓库级搜索，而不只检查 diff？
7. 它最终交付的是一个自洽状态，还是“新方案 + 一堆旧方案否定句”？
